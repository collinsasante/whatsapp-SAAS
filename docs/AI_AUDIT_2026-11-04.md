# AI completion audit: partial, code-level (2026-11-04)

Scope of this pass: reading the code on `origin/staging` (5ff4a0e) plus the two candidate branches, and the unit suites that already exist. **No real provider call, no real-PostgreSQL BullMQ run and no end-to-end conversation was made in this pass**, so nothing below is a production-readiness claim.

## Verified in code
| Area | Finding |
|---|---|
| v1/v2 architecture | `MessagesService.generateAiReply` picks Commerce AI for commerce tenants, otherwise the v2 pipeline when the per-tenant feature flag `verz_ai_v2` is on, otherwise the legacy `AiResponderService`. **v1 is still live** for every non-commerce tenant without the flag, and `/ai-logs/test` (sandbox) calls the legacy responder directly. "v2-only" is not true yet. Rollout is by per-tenant feature flag (`FeatureFlagsService.isEnabledCached`), not an environment allowlist. |
| Prior staging validation | Memory of 2026-11-01: v2 confirmed on staging but 2 of 4 replies rejected as malformed (tool path vs JSON prompt), which blocked v1 retirement. Parser-hardening commits landed since (3f8c8a2 and others on `origin/staging`); **not re-validated on staging after them**. |
| Duplicate provider calls / concurrency | `conversationAiLocks` chains AI turns per conversation, **in process only**. Correct for one backend replica; two replicas could generate concurrently (documented limitation in the code). Inbound messages are de-duplicated by provider message id before AI is triggered. |
| Credits | Durable reservations (`reserveFixedCredits`, `settleReservation`, `releaseReservation`, migration `ai_credit_reservations`): credits are held before the provider call, settled after, released only on a definitive 4xx rejection and kept (conservative expiry) on uncertain outcomes. This protects against double spend and concurrent overspend. A tenant's credit balance is the effective spend cap; no separate per-tenant budget or alerting threshold was found. |
| Prompt injection | One canonical pattern list (`ai-core/guards/injection-patterns.ts`) shared by v2 guard, Commerce, legacy and the sandbox; input is NFKC-normalised and zero-width characters removed. Pattern-based only, so it is a first filter, not a security boundary: the real controls must be tool permissions and tenant scoping. |
| Tools | Registered per capability (`resolveToolNames`, `readOnlyTools` flag); `ToolCallingService` caps iterations at 4, tool-call arguments are parsed defensively and "the tool handler validates required fields". The tenant id comes from the pipeline context, not from model output. Execution-time validation inside each handler was **not** audited tool by tool. |
| Traces | Every pipeline run persists an `AiExecution` trace (also on error), tool traces are sanitised (`tool-trace-sanitizer.util.ts`). |
| Existing tests | The quality harness (`ai-core/quality`) and unit suites run in the 2088-test backend suite (all passing on the candidate branch). They use mocked providers. |

## Not audited yet (genuinely open)
Image, caption-only image and voice-note handling; input/output redaction and context limits; conversation memory and knowledge-base retrieval quality; per-tool execution-time authorization; BullMQ retry/idempotency of AI jobs on a real PostgreSQL; malformed-response and timeout paths against a real provider; real-provider end-to-end quality. These need either deeper review or provider credentials and a staging window.

## Recommended before calling AI production-ready
1. Re-run the v2 staging validation (4+ real conversations incl. tool path) on the current build; 2. a Redis-backed conversation lock, or confirm single replica as policy; 3. a per-tenant spend alert/cap decision; 4. tool-by-tool authorization review; 5. media (image/voice) end-to-end on staging.
